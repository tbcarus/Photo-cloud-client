# A1 — Resumable upload на Android Camera

Дата: 2026-11-14. Реализован Android-клиент для существующих Camera-фото. Видео Camera, автоматические SAF-источники, ручная Library и UI выбора сети не менялись. Коммиты не создавались.

## Возможности и архитектура

Camera выбирает multipart для файла до 50 MiB включительно, resumable — свыше 50 MiB до 20 GiB включительно. Размер 0/неизвестный даёт `FAILED / SIZE_UNKNOWN`, свыше 20 GiB — `FAILED / FILE_TOO_LARGE`. Значения находятся в `SyncConfig` вместе с блоком 8 MiB.

`ResumableUpload` выполняет протокол S1: устойчивый `clientRequestId`, идемпотентное создание, GET состояния при возобновлении, последовательные PATCH с подтверждённого смещения, complete и ожидание `COMPLETED` с квитанцией. Блок стримится из URI через seekable-дескриптор, не хранится целиком в памяти. `ChunkBody` открывает поток при каждом `writeTo`, включая повтор OkHttp после обновления токена. Асинхронный Retrofit Call отменяется при остановке coroutine/Worker.

Отдельный `CameraUploadSource` проверяет MediaStore size, DATE_MODIFIED и режим оригинала до передачи и перед каждым следующим блоком. Только подтверждённое изменение/удаление ведёт к DELETE прежней сессии; отсутствие разрешения, неподключённый том и сбой чтения остаются временными. После изменения исходника файл возвращается Поставщику на новый hash. Несовпадение полного SHA-256 на Server проходит существующий Q-02: до трёх автоматических восстановлений, затем `FAILED / CHANGED_DURING_UPLOAD`.

`upload_sessions` в Room не связана внешним ключом с `media_files`: исчезновение Camera-строки не удаляет ID незавершённой сессии. Запись хранит Server URL, subject аккаунта, MediaStore ID/URI, снимок версии, checksum, папку, `clientRequestId`, серверный UUID, локально известный offset и запрос на отмену. `clientRequestId` сохраняется до первого POST; полученный UUID и смещение сохраняются перед следующим запросом. При новом запуске offset обязательно уточняется GET. Старые записи другого Server/аккаунта не переиспользуются; их можно отменить после возврата к соответствующей учётной записи.

Для resumable Camera нужен активный Wi-Fi. Новые HTTP-сокеты, DNS и запрос refresh привязаны к выбранной Wi-Fi сети; при её потере передача приостанавливается. Поведение остальных загрузок не изменено. Текущий ping Server может выполняться до этой проверки; байты нового resumable-протокола через мобильную сеть не отправляются.

## Переиспользовано из A8

Сохранены Provider scan/hash, pre-check, FIFO по MediaStore ID, выборка по 20, один Upload-прогон под Mutex, `WorkBudget`, штатное продолжение через `SyncScheduler`, retry/backoff WorkManager, условные переходы `MediaFileDao`, а также пауза Q-01 и ограничение восстановления Q-02. Отдельного Worker для больших файлов нет. После подтверждённого блока и исчерпания бюджета следующая работа регистрируется как обычное продолжение; без нового прогресса действует retry/backoff. Следующий файл не начинается до окончания текущего.

## Изменённые компоненты

- `FileUploadRepository`: выбор протокола, обработка результата/ошибок, отмена устаревших сессий и сохранение FIFO.
- `ResumableUpload`, `UploadSessionService`, `UploadSessionRecord`, `CameraUploadSource`, `WifiUploadNetwork`: протокол, HTTP DTO, Room, адаптер MediaStore и сеть.
- `MediaStreamOpener`: повторное открытие потока с seek к offset; `ApiServiceFactory` и `TokenAuthenticator`: Wi-Fi-bound запросы и refresh.
- `AppDatabase`: схема 10 и миграция 9→10; `AppModule`: DAO; `SyncConfig`: единые пределы; `FailureReason`/Files UI: явные причины пропуска.
- System SPEC: модель UploadSession, BACKUP-RESUMABLE/BACKUP-UPLOAD, правила восстановления и индекс статусов. `FILES-RESUMABLE` для Library остаётся SERVER_ONLY.

## Отказы и восстановление

| Событие | Действие |
| --- | --- |
| Потерян ответ create | Повтор POST с тем же сохранённым `clientRequestId` |
| Обрыв PATCH или потерян ответ | GET; уже подтверждённые байты не передаются снова |
| Потерян ответ complete | GET; `SYNCED` только после `COMPLETED` и проверенной квитанции |
| `FINALIZING` | Ограниченное ожидание в текущем прогоне, затем продолжение или backoff |
| Worker остановлен во время HTTP | Call отменяется, Room-запись остаётся; следующий прогон делает GET |
| Server удалил/истёк | Локальный ключ удаляется; следующий прогон создаёт новую сессию и новый UUID |
| Исходник изменён/удалён | Прежняя сессия отменяется; даже без Camera-строки запись остаётся до ответа Server |
| Нет доступа или временно недоступен том | Сессия и Camera-строка сохраняются, отмена не предполагается |
| Нет Wi-Fi или сменился аккаунт/Server | Передача не продолжается в другом контексте; состояние остаётся в Room |

## Проверки

Полная регрессия `:app:testDebugUnitTest` с `PHOTO_CLOUD_A1_S1_SMOKE=1` прошла: 759 тестов в 83 наборах, 0 ошибок, 0 пропусков. Адресные тесты проверяют границы 50 MiB/20 GiB и явные причины пропуска, Room reopen и изоляцию аккаунта/Server, несколько блоков и неполный последний, потерянные create/PATCH/complete, повтор HTTP-тела после 401, бюджет и распознанный по GET прогресс после перезапуска, изменение/удаление исходника против временной недоступности, отмену сиротской сессии, отсутствие Wi-Fi и отмену зависшего Call. Существующие тесты Camera FIFO, Q-01 и Q-02 включены в полную регрессию.

Изолированный smoke Android-протокола с настоящим S1 Server прошёл: отдельный процесс Server на случайном порту (не 8080), временный Docker PostgreSQL и storage, два блока (8 MiB + 3 байта), `COMPLETED` и скачанные байты. Он запускается явно: `PHOTO_CLOUD_A1_S1_SMOKE=1` для `ResumableUploadS1SmokeTest` и требует собранный Server `bootJar`. Рабочие Server, БД, storage и пользовательские медиа не использовались.

## Ограничения и дальнейшие этапы

- На устройстве, после реальной перезагрузки и на мобильной сети прогон не проводился; Room/WorkManager и Wi-Fi поведение проверены тестами и кодом, но не устройством.
- Файл не закрепляется как неизменяемый снимок. При изменении байтов без изменения size/DATE_MODIFIED несоответствие выявляет SHA-256 Server; прежние ограничения Q-02 сохраняются.
- Полный файл 20 GiB и нагрузочный прогон не выполнялись. Хеширование исходника остаётся стадией Provider до передачи.
- При смене аккаунта или Server прежняя запись сохраняется для отмены при возвращении; серверный TTL остаётся страховкой, если возврата нет.
- SAF, Library и видео потребуют отдельного подключения к общему протоколу. Для SAF/Library прежний multipart в диапазоне 50–100 MiB пока получает 413.
